# Architecture

How Gestão Escolar is put together: the modules, the data model, how a request
is handled, the financial rules, and the UI conventions. For setup, see
[README.md](README.md).

This Next.js app replaces the Django project in `../../django/gestao`, which
is now **legacy**: it is kept only as the reference for the rules and the
screens not ported yet. The database schema is owned by Drizzle migrations
(`drizzle/`). The business rules below came from it unchanged; when this
document and the Django code disagree on a rule, the Django behavior is the
reference and the difference is a bug here.

## Overview

A single Next.js 16 app (App Router, Cache Components) in TypeScript. Pages
are **Server Components** that query PostgreSQL through **Drizzle**; writes are
**Server Actions**. Client components are used only where the page needs state
in the browser (pickers, forms with rows added on the client, comboboxes).
Styling is **Tailwind CSS 4** plus **Flowbite React**. Authentication is
**Better Auth** (username + password, sessions stored in Postgres).

```
Browser ──HTTP──▶ src/proxy.ts (valid session?) ──▶ src/app/(app)/<route>/page.tsx
                                                       │ requireSession(), Drizzle queries
                    HTML (RSC)  ◀──────────────────────┘
form submit ──▶ Server Action (actions.ts) ──▶ requireSession() → parseForm(zod) → db.transaction
                                           └─▶ redirect(listPath?msg=created|updated|deleted|protected)
```

## Data model

> The rules in this section and the next two (enrollment → finance, bank
> slips) are copied from the Django project and still hold.
> Names like `enrollment_amounts()` in `accounts/services.py` refer to the
> Django code; their TypeScript ports keep the same name in camelCase
> (`enrollmentAmounts()`) in the `src/lib/` module listed in [Modules](#modules).
> Screen URLs are the Django ones; the Next route is the matching folder under
> `src/app/(app)/` (kebab-case, `/new` and `/[id]/edit` instead of `add/` and
> `edit/<pk>/`).

### Shared abstract models (`base/models.py`)

- **`TimeStampedModel`**: `created_at`, `updated_at`.
- **`Person(TimeStampedModel)`**: name, sex, CPF and RG (both unique), issuing
  authority, birth date, nationality, place of birth, phone, mobile, email,
  and address (street, neighborhood, city, UF, CEP). Used by `Employee`,
  `Student` and `Guardian`. Documents are stored **digits only**.

### Academic models

| Model | Key fields and rules |
|---|---|

| `Class` | program, school year, optional grade level (1–3), name, shift (`M/T/N/I`), capacity. Unique per (year, program, name) |
| `Student(Person)` | `registration` auto-generated as `<year><5-digit sequence>` (e.g. `202600001`); social name; photo saved as `media/students/<registration>.<ext>`, with the old file removed on change and a placeholder when missing |
| `Guardian(Person)` | marital status |
| `GuardianAssociation` | student ↔ guardian with relationship and flags: `is_financial`, `is_primary_contact`, `living_with`, `pick_up`. Unique per pair |
| `EnrollmentType` | contract template: program, level, school year, `total_price`. Contract dates default to the school year's |
| `DiscountType` | description and percentage (0–100) |
| `Enrollment` | student, contract type, optional class, status (`A` active, `T` transferred, `D` dropped, `C` completed, `X` cancelled), date, `due_day` (1–28). The first installment is 1/12 of `gross_value` less its own discount; the other 11/12, less theirs, are split over the remaining installments (`enrollment_amounts()` in `accounts/services.py`; a single December installment carries both parts). Unique per (student, contract type) |

Each one has a `group`: `F` first installment or `R` remaining installments; the groups are independent (same, other or no discounts). Percentages are added per group; each sum can't pass 100%. Chosen only on creation, read-only afterwards. Unique per (enrollment, group, type) |
| `EnrollmentNeededDocument` | one row per required document type per enrollment, with `is_delivered` |
| `Department` (`departments`) | `name` unique; `teachers` (many-to-many to `Employee`; a teacher can be in several departments). Can't be deleted while subjects use it |

### Grade models (`grades/models.py`)

| Model | Key fields and rules |
|---|---|
| `ExamType` | name and `code` (both unique, code upper-cased by the form), `kind` (`R` avaliação, `B` ponto extra, `C` recuperação), `max_score` (> 0), `order` (column order). There are no weights: each exam's `max_score` is its share of the bimester (e.g. PS 3, PB 6, comportamento 1) |
| `GradeLevelSubject` | a subject taught in every class of a series (`grade_level` 1–3, matched against `Class.grade_level`), with **several teachers** (`teachers`, many-to-many to `Employee`, limited to the teachers of the subject's department) and classes per week (decimal, ≥ 0: a weekly mean such as 1,5). Unique per (series, subject). The report card's rows and the grade entry subjects come from it; a class without a series has no subjects |
| `Grade` | **enrollment** (not student: it fixes year and class), subject, exam type, bimester (1–4), `score` (0 to the exam's `max_score`). Unique per (enrollment, subject, exam type, bimester). `clean()` requires the subject to be taught in the series of the enrollment's class |

Grades and averages are never stored; `grades/services.py` computes them per
request:

- `bimester_grade(grades)`: **sum** of the `R` and `B` scores, capped at 10
  (so extra points can't go past 10). `C` scores don't count. `None` without
  any `R` score. Rounded half-up to cents.
- `final_average(grades)`: the **annual average**, the weighted mean of the four
  bimester grades (20%, 30%, 20%, 30%) rounded to the half point (.25 → .5,
  .75 → next whole), `None` until all four exist. `PASSING_GRADE` is 6.00.
- **Final recovery**: a student whose annual average is below 6 takes the
  recovery exam (`C`) of that subject. Its grades are stored with
  `bimester = FINAL_RECOVERY` (5, "Recuperação final"); `Grade.clean()` keeps
  `C` exams in that period and every other exam out of it. `final_grade(average,
  recovery)` is the mean of the average and the recovery score, rounded to the
  half point; the student passes when it is ≥ 6. A recovery score is ignored
  when the average is already ≥ 6.
- `report_card(enrollment)`: one `ReportCardRow` per subject of the class's series (4 bimester grades,
  `average`, `recovery`, `final`, `passed`), in two queries. `passed` is `None`
  while the year is incomplete or the recovery score is missing ("Em recuperação").

`Enrollment.clean()` requires the student to have a **financial guardian**, and
the class to match the contract's year, program and grade.

### Incident models (`incidents/models.py`)

Conduct records point at an **enrollment**, not a student, for the same reason
as `Grade`: the enrollment fixes the school year and the class
(`enrollment.school_class`). Each has an `incident_date` (the day it
happened, which can differ from `created_at`).

| Model | Key fields and rules |
|---|---|
| `IncidentType` | `type` unique, `penalty` (decimal, ≥ 0, `CheckConstraint`) |
| `Incident` | enrollment (`related_name="incidents"`), incident type, `incident_date` |
| `StudentDelay` | enrollment (`delays`), `delay_type` (`A` tolerado, `U` não tolerado), `incident_date` |
| `BathroomPermission` | enrollment (`bathroom_permissions`), `class_period` (the lesson, ≥ 1, checked by the form), `incident_date` |

The forms share `ActiveEnrollmentFormMixin` (`incidents/forms.py`): the
enrollment select lists only active enrollments, plus the record's current one
when editing. The lists search by student name and show the class.

### Q&A session model (`q_and_a/models.py`)

`QandA` (plantão) records that a student attended a subject's Q&A session:
enrollment (`related_name="q_and_as"`), subject (`grades.Subject`,
`related_name="q_and_as"`) and `q_and_a_date`. Like the incident models it
points at an enrollment and its form reuses `ActiveEnrollmentFormMixin`. The
list searches by student or subject name and filters by subject and date range
(`QandAFilterForm`).

### Pathway models (`pathways/models.py`)

Extra-curricular courses. A student picks pathways every year, with no
contract or installments. Some pathways give an extra grade in the bimester,
chosen by their teachers; others never do.

| Model | Key fields and rules |
|---|---|
| `Pathway` | catalog: `name` unique, `description`, `extra_points` ("Nota máxima", ≥ 0: the highest grade its teachers can give in a bimester; 0 means it gives no extra grade, `gives_grade`), `workload_type` (`N` sem carga horária, `F` fixa, `P` por presença) and `workload_hours` (the year's hours, > 0 only when fixed; a `CheckConstraint`, and `clean()` zeroes it for the other types) |
| `PathwayOffering` | a pathway running in a `SchoolYear`: optional `name` (to tell groups apart), `teachers` (many-to-many to `Employee`), optional `capacity`, `schedule` (free text), `weekdays` (JSON list of `lessons.Weekday` values, 1–6; `clean()` rejects others and sorts them; they build the diary's dates). Unique per (pathway, year, name) |
| `PathwayEnrollment` | **enrollment** × offering, `joined_at`, `left_at` (leaving sets it instead of deleting). Unique per pair. `clean()` requires the offering to be in the enrollment's school year and a free seat (members without `left_at`) |
| `PathwaySession` | a lesson (aula): offering, `date` inside the school year, optional `topic` |
| `PathwayAttendance` | session × pathway enrollment, `status` (`P` presente, `F` falta, `J` falta justificada). Deleted with its session. `clean()` requires the same offering and membership on the lesson's date |
| `PathwayGrade` | the points the pathway teacher gives per pathway enrollment and bimester (1–4), from 0 to the pathway's `extra_points`; `clean()` rejects grades in a pathway that gives none. Unique per (pathway enrollment, bimester) |

**Extra grade** (`pathways/services.py`, like the concept grade): for each
enrollment and bimester, the pathway grades are added as the teachers gave
them; a pathway without a grade, or one that gives no extra grade, adds 0.
Attendance is recorded and shown but never changes the grade. Q&A sessions
don't count: their grades are entered by hand. The sum is capped at the max score of the
`EX` exam type and `save_extra_grades()` writes it, zero included, to every
subject of the series through `grades.services.save_series_grades()` (shared
with `save_concept_grades()`). `EX` is therefore calculated, not typed.

**Workload** (`workload()` / `year_workload()` in `pathways/services.py`,
computed per request): a fixed pathway gives its hours to everyone who was in
it at any point of the year, even after leaving; a per-attendance one gives
45 minutes (`LECTURE_HOURS`) per lesson marked present (`J` earns nothing).
The student attendance screen shows the year total.

**Screens** (sidebar section "Itinerários", `base/sidebar/menu/itinerarios.html`):
standard CRUDs for pathways (`pathways/`), offerings (`pathways/offerings/`,
filter by year and pathway, with links to the offering's roster, lessons,
grades and diary) and the roster (`pathways/enrollments/`, filter by offering and
situation). Roster and lessons take `?offering=<pk>` to prefill the form and
return to the filtered list; with the offering known, the enrollment select
lists only that year's active enrollments. Leaving is recorded with `left_at`;
deleting a member with attendance or grades is blocked.

- **Sign up a student** (`pathways/enrollments/by_student/?enrollment=<pk>`,
  `StudentPathwaysForm`, sidebar "Inscrever aluno"): pick an active enrollment,
  then tick the year's offerings. Full offerings are disabled unless the
  student is already in them. Unticking sets `left_at` (or deletes a pathway
  enrollment that hasn't started and has no attendance or grades); ticking a
  left one again clears `left_at`. One invalid row saves nothing.
- **Diary** (`pathways/offerings/diary/<pk>/?bimester=N`, `PathwayDiaryView`):
  a standalone printable page (doesn't extend `base.html`), opened in a new
  tab from the offering list. Columns are the bimester's dates on the
  offering's `weekdays` (`lesson_days()` in `pathways/services.py`), rows the
  members in that bimester, with the days they weren't members blanked.
  Defaults to the current bimester. Holidays aren't removed: there's no
  calendar.
- **Lessons** (`pathways/sessions/`): "Nova aula" saves the lesson and opens
  its roll call (`sessions/attendance/<pk>/`, `AttendanceSheetForm`): one status
  per student in the pathway on that date, present by default. A lesson's
  offering can't be changed; moving its date removes the attendance of students
  who weren't in the pathway then. The list shows present and absent counts,
  or "Sem chamada".
- **Student workload** (`pathways/workload/by_student/?enrollment=<pk>`,
  `StudentWorkloadView`, sidebar "Carga horária do aluno"): pick an active
  enrollment; lists each of its pathways in the school year with type,
  presences and hours (`with_workload()`), and the total in the footer. Not
  paginated, so the total always matches the rows.
  "Imprimir" opens `pathways/workload/print/<pk>/` (`StudentWorkloadPrintView`),
  a standalone A4 report with the letterhead, like the diary.
- **Pathway grades** (`pathways/grades/entry/`): pick offering and bimester;
  only pathways that give an extra grade are listed. `PathwayGradeSheetForm`
  has one optional grade (0 to the pathway's `extra_points`) per student in the
  pathway during the bimester (blank deletes), and shows each one's attendance
  (`P / (P + F)`, `J` left out) for reference.
- **Extra grade** (`pathways/extra_grades/all/` and `individual/`): the concept
  grade screens (`IncidentGradesAll` / `IncidentGradesIndividual`), subclassed
  through their `get_exam_type()`, `save_grades()`, `exam_type_missing` and
  `url_name` hooks.

### Lesson models (`lessons/models.py`)

The regular lessons of a class: 12 periods a day Monday to Friday and 7 on
Saturday (`LECTURES_PER_DAY`, `SATURDAY_LECTURES`). Only classes with a series
(`grade_level`) have them, since only they have subjects. `weekday_periods()`
gives the periods of a weekday and `period_error()` refuses a Saturday period
past the 7th; loop over `weekday_periods()`, not `PERIODS`, when building a
day.

| Model | Key fields and rules |
|---|---|
| `TimetableSlot` | class, `weekday` (1–6, `Weekday`, Monday to Saturday), `period` (1–12, `PERIODS`; 1–7 on Saturday, also a `CheckConstraint`), `subject` (`GradeLevelSubject`), `teacher`. Unique per (class, weekday, period). One timetable per class, valid for its year; editing it never changes saved lectures. `clean()` requires a period the weekday has, the subject in the class's series, the teacher among the subject's `teachers`, and no other class of the same year **and shift** with that teacher in that weekday and period |
| `Lecture` | class, `date`, `period`, `subject`, `teacher`, `topic` (required). Unique per (class, date, period). Subject and teacher are copied from the timetable, so a substitution only changes the lecture. `clean()` requires a Monday-to-Saturday date inside the class's school year (`lecture_date_error()`), a period that day has, the subject in the class's series and a teacher from `lecture_teachers()`: the subject's teachers or any teacher of its department |

Days without lectures (holidays, events) simply have no rows: there's no
calendar. `lessons/services.py` builds the timetable grid and `weekly_load()`,
the periods scheduled per subject against `GradeLevelSubject.weekly_classes`
(a weekly mean, so a mismatch is only a warning).

**Screens** (sidebar section "Acadêmico"):

- **Timetable** (`lessons/timetable/?school_class=<pk>`): the 6-day grid
  (12 rows; Saturday's cells past the 7th period are empty) and the weekly
  load. `timetable/edit/<pk>/` (`TimetableForm`) has one
  "Matéria — Professor" select per cell, built from the series' subjects ×
  their teachers; a blank cell deletes the slot. The whole grid is validated
  before anything is saved.
- **Day sheet** (`lessons/lectures/day/?school_class=<pk>&date=<iso>`,
  `LectureDayForm`): a row per period of that weekday (12, or 7 on
  Saturday), prefilled from the saved lecture or the
  timetable. Rows with a topic are saved, clearing a topic deletes the lecture,
  and one invalid row saves nothing. This is the only way to add lectures.
- **Class diary** (`lessons/lectures/list/`): filters by year, class, subject,
  teacher and date range; search by topic. Edit and delete one lecture.

Attendance per lecture is not built yet; it would be a
`LectureAttendance(lecture, enrollment, status)` deleted with its lecture.

### Financial models (`accounts/models.py`)

Money is always `DecimalField(max_digits=10, decimal_places=2)` (the `MONEY`
constant). Never use floats.

| Model | Key fields and rules |
|---|---|
| `AccountType` | financial category, with `direction` `R` (receivable) or `P` (payable). Name unique |
| `Supplier` | name, CPF/CNPJ (digits, unique when filled), contacts |
| `Account` | `direction`, description, category, issue date, `gross_value`, `discount_value`, notes. Counterpart: `student`, `guardian` and/or `enrollment` for receivables, `supplier` for payables, enforced by a DB check constraint. When a receivable has a student, its guardian must be one of the student's financial guardians (the form fills in the first one if left empty). `net_value = gross − discount` |
| `AccountReceivable`, `AccountPayable` | **proxy models** of `Account`, each with a manager filtered by direction and a `save()` that sets it. Views and forms use these |
| `Installment` | account, `number` (unique per account), `due_date`, `amount`, `status`: `A` open, `P` partially paid, `Q` paid, `C` cancelled, `E` expired (bank wrote off the unpaid slip; still owed). `PENDING_STATUSES` = open, partial, expired |
| `Payment` (baixa) | installment, `paid_at`, `amount` (total received, **including** penalty, interest and monetary adjustment), the three charges, `discount` (e.g. punctuality; settles principal without being received), method (PIX, boleto, cash, card, transfer, check) |

**Integrity rules**

- Every financial FK is `on_delete=PROTECT`. Deleting something that's in use
  shows a message instead of an error (`ProtectedDeleteMixin`).
- Principal paid = `amount − penalty − interest − monetary_adjust + discount`.
  `PaymentForm` won't let the principal go over the installment's balance or
  drop to zero or below.
- `Payment.save()` and `delete()` call `Installment.refresh_status()`, which
  sets the status from the principal paid (open → partial → paid). Cancelled
  installments are never changed by it; expired ones only move to paid.
- An account's `gross_value` and `discount_value` are locked after creation,
  because they were already split into installments.
- A category's `direction` is locked once accounts use it.
- An account with payments can't be deleted. Without payments, its
  installments are deleted with it.

**Query helpers**

- `Account.objects.with_installment_summary()` annotates installment counts
  (total, pending, overdue, paid) used by `Account.situation` and the status
  filter, without N+1 queries.
- `Installment.objects.with_balance()` annotates `outstanding` in SQL (same
  rule as `Installment.balance()`), via a subquery so it can be summed.
  Also `.pending()` and `.overdue()`.
- "Overdue" depends on today's date, so it's always computed per request,
  never stored.

## Enrollment → finance workflow

Implemented in `enrollments/signals.py` and `accounts/services.py`.

1. **Enrollment created** (`post_save`, `created=True`):
   - `create_enrollment_account()` creates an `AccountReceivable` in category
     "Mensalidade" (created if missing), linked to the enrollment, its
     student and the student's first financial guardian, using the contract's values.
   - It generates monthly installments, with due dates from
     `enrollment_due_dates()`. They fall on `due_day` of the **school year**,
     moved to Monday when that day is a weekend
     (`utils.format.weekdays.adjust_weekend`):
     - enrolling during the school year: the first is due on the enrollment
       date, then one per remaining month, through December (enrolled on
       Sep 15 → Sep 15, Oct, Nov, Dec);
     - enrolling ahead (e.g. November 2026 for 2027): 12 installments,
       January to December 2027.
   - The net value is split with `split_value()`: every installment gets the
     value rounded down to the cent, and the first gets the remainder, so
     installments always add up to the account's net value.
   - `sync_documents()` creates one `EnrollmentNeededDocument` per required
     document type.
2. **Enrollment changed to transferred, dropped or cancelled**:
   `cancel_future_installments()` cancels the account's **open** installments
   due today or later. Partially paid ones are kept.
3. The **enrollment edit page** shows the documents checklist and the
   installments as inline formsets, saved in one transaction.

Accounts created by hand use `build_installments()` instead: the net value is
split into N monthly installments starting on the chosen first due date, with
the same `split_value()` rounding.

## Bank slips (`billing`)

Bradesco "Cobrança" in CNAB 400. `billing/cnab400.py` is pure Python (no
Django): it writes remittance files and parses return files. Its fixed values
match files the bank already accepted (`00000 000000000000 ` in positions
2–20, `N` in 94, `2` in 106, CRLF line endings, no EOF byte).
`billing/services.py` holds the workflow:

1. **Settings** (`BankSettings`, single row edited at `settings/edit/`):
   company code, wallet, agency/account, fine % (2), monthly interest % (1),
   and the last remittance number.
2. **Remittance** (`create_remittance`): one `.REM` carries new slips
   (movement `01`) and write-off requests (movement `02`). Candidates for new
   slips are receivable installments with status in `PENDING_STATUSES`, a
   balance, and no *live* slip (generated, registered or write-off
   requested). Installments whose financial guardian lacks a
   valid CPF, address or CEP, or whose due date has passed, are listed but
   skipped. Each slip gets nosso número `2000` + slip id (11 digits) plus its
   check digit; participant control = slip id; document number =
   installment id. The amount is the outstanding balance; daily interest =
   amount × monthly % / 30; the punctuality discount comes from
   `EnrollmentType.punctuality_discount` (only for enrollment accounts, valid
   until the due date). The file is stored in `Remittance.content` and
   downloaded as `<number:08>.REM`. A remittance the bank hasn't processed
   (new slips still "generated", write-offs still "requested") can be
   deleted: its write-offs go back to "registered", and the number is freed
   if it was the last.
3. **Write-off request** (pedido de baixa): `write_off_candidates()` lists
   registered slips whose installment was cancelled or paid another way
   (balance below the slip amount, e.g. paid in cash). Selected slips are
   sent again with movement `02` and become "write-off requested", which is
   still live: the installment gets a new slip only after the bank confirms
   with `10`. A partially paid installment is then resent for its balance.
4. **Return** (`import_return`): rejects other company codes and files already
   imported (sha256); lines already seen (fingerprint) are skipped. Slips are
   matched by nosso número; lines from the previous system (another prefix)
   are stored as *ignored*. Per occurrence code:
   - `02` slip registered; `03` slip rejected (installment can be resent);
   - `06`/`15`/`17` creates a `Payment` (method boleto) with the bank's
     interest and discount, so principal = paid − interest + discount. A
     principal above the balance, a cancelled installment or a slip already
     settled is flagged as an *error* for manual handling;
   - `22`/`40` deletes that payment (installment reopens), slip reversed;
   - `09` slip expired and the installment set to **expired**;
   - `10` slip written off, confirming a write-off request (a message is left
     if the installment still has a balance, so it can be resent);
   - `27` write-off rejected: the slip goes back to registered;
   - other codes are stored as *ignored*.
   Each line runs in a savepoint, so one bad line doesn't stop the file.

## Development data (`npm run db:reset`)

`scripts/reset-db.mts` drops the `public` and `drizzle` schemas, re-runs the
migrations in `drizzle/` and loads `scripts/seed.mts`. It refuses any
`DATABASE_URL` whose host isn't `localhost`, so it can't reach Neon.

The seed is deterministic (a fixed-seed PRNG) and dated from today, so the
current school year always has finished bimesters with grades, paid and
overdue installments, and recent records:

- Users through Better Auth's API (`auth.api.createUser`): `admin` (role
  `admin`) and `secretaria`, password `SEED_PASSWORD` (default `senha1234`).
- Reference data: the program, this year's and next year's school years with
  bimester dates, enrollment types per series, documents, discounts, the exam
  types of Django's seed (`PS`, `PB`, `C`, `EX`, `A`), incident types, roles,
  account categories and two suppliers.
- One teacher, department and subject per discipline, with the subject offered
  in all three series.
- Two classes per series, six students each with a financial guardian (one
  self-financial adult), some with discounts. Enrollments go through
  `createEnrollmentAccount()` and `syncDocuments()`, payments through
  `refreshInstallmentStatus()`: installments already due are paid, except a
  few debtors (overdue) and some partial payments.
- `PS` / `PB` grades for the finished bimesters, incidents, delays, bathroom
  permissions and Q&A sessions, a Monday–Friday timetable with the last two
  weeks of lectures, and two pathways with weekly sessions, attendance and
  bimester grades. Concept and `EX` grades are left to the "calcular" screens.

## Request handling

### Pages and actions

- Routes follow one pattern per resource, under `src/app/(app)/`:
  `/<resource>` (list), `/<resource>/new`, `/<resource>/[id]/edit`. Deleting is
  a Server Action called from the list's row menu, not a page. Pattern to
  copy: `src/app/(app)/programs/`.
- Pages are Server Components. `src/app/(app)/layout.tsx` calls
  `requireSession()` (`src/lib/session.ts`) for the whole tree; edit pages
  read the id with `idParam(params)` (`src/lib/list.ts`).
- Mutations are Server Actions in the route's `actions.ts`. Each one calls
  `requireSession()` first, parses the form with
  `parseForm(schema, formData)` (zod, `src/lib/form.ts`), runs multi-table
  writes in `db.transaction()`, maps a Postgres `UNIQUE_VIOLATION` to a field
  or form error, and redirects with `?msg=created|updated|deleted`.
- Deletes go through `deleteAndRedirect(() => …, listPath)` (`src/lib/crud.ts`),
  which turns a foreign key violation (Django's `PROTECT`) into
  `?msg=protected`. Django deletes many-to-many links implicitly; here they are
  deleted first, in the same transaction (see `employees/actions.ts`).
- Flash messages: `<Flash>` (`src/components/flash.tsx`) reads `?msg=` and
  shows the text Django showed ("Registro cadastrado com sucesso", …).

### Authentication

Better Auth (`src/lib/auth.ts`) owns authentication: sign-in by username
(`username` plugin), password hashing (its default scrypt), sessions in the
`session` table, and the `admin` plugin for roles and banning. Sign-up is off;
users are created with `auth.api.createUser` (the seed does this).

`src/proxy.ts` asks Better Auth to validate the session on every request
(`auth.api.getSession`: signature, expiry, revocation, banned user) and
redirects to `/login?next=…` otherwise. That check has to live there, not only
in a layout: a layout doesn't stop its page from rendering into the response.
Server Actions also call `requireSession()`, since they are POST endpoints.

### Lists, search and filters

- `<ListPage>` + `<ListRow>` (`src/components/list-page.tsx`): heading, main
  action, search, the table and pagination. Search, filters, sort and page are
  query params, so they survive reloads and the back button.
- `searchWhere(query, columns)`, `pageParam`, `sortParam` and `PAGE_SIZE`
  (`src/lib/list.ts`). Search across related rows with `EXISTS` (see
  `departments/page.tsx`), not joins that duplicate rows.
- Filter controls: `SearchBox`, `FilterSelect`, `FilterDate`, `SortHeader`,
  `ListPagination` (`src/components/list-controls.tsx`).
- Raw SQL subqueries reference the outer row with `ref(column)`
  (`src/lib/sql.ts`): in a single-table select Drizzle writes a bare `"id"`,
  which inside a subquery binds to the subquery's own table.
- Account lists use `accountSummary()` / `accountStatusWhere()` and
  `paidPrincipalSql` from `src/lib/finance-db.ts` (Django's
  `with_installment_summary()` and `with_balance()`), never a query per row.

### Dependent pickers

"Pick A, then B filtered by A" screens (class roster, grade entry, timetable,
day sheet) are client picker components (`classes/detail/class-picker.tsx`,
`grades/entry/grade-picker.tsx`, `lessons/class-picker.tsx`) that push the
selection into the URL; the Server Component page reads it from
`searchParams` and renders the table. A reload rebuilds the page from the URL.
Client components that read the URL must sit inside `<Suspense>`.

The class roster lists the students with an **active** enrollment in the
selected class, and shows the subjects and teachers of the class's series
(read-only), linking to "Matérias por série" (`grades/level-subjects`). In that
form the teacher checkboxes are limited to the subject's department (none,
with a help text, when the subject has no department).

### Grade entry (`grades/entry/`)

Four selects: year → class → subject → period (the four bimesters plus
"Recuperação final"). A class that isn't in the chosen year and a subject the
class's series doesn't have are dropped from the selection. A bimester sheet
has every exam type but the `C` ones; the final recovery sheet has only the
`C` ones and only the students whose annual average is below 6, with their
average and resulting final grade.

The sheet has one optional decimal cell (comma decimals) per active
enrollment × exam type. On submit, any invalid cell saves nothing; otherwise
grades are created, updated or (for an emptied cell) deleted in one
transaction. The report card (`grades/report-card/[id]`) is linked from the
enrollment edit page.

### Concurrency

Payments lock their installment with `lockInstallment()`
(`src/lib/finance-db.ts`), which locks first and reads the balance in a second
statement: under READ COMMITTED a subquery in the locking statement keeps the
old snapshot and would miss a concurrent payment.

### Uploads

Student photos are written to `MEDIA_ROOT` (a local folder; on Vercel the disk
is not persistent, so photos need object storage before going live) and served only to signed-in users by
`src/app/media/[...path]/route.ts`. Images are validated by magic bytes
(`src/lib/media.ts`).

## Design system

Light only, gray neutrals on a `bg-gray-50` canvas, white cards, Flowbite
React components themed through Tailwind. Font: Geist (`next/font`). Icons:
**Material Symbols Outlined**, the same set the Django templates used. The
action color is navy: the `--primary-*` scale in `globals.css` replaces
Flowbite's blue, so code uses `primary-*` classes, never `blue-*`. Icons are
gray (`[data-tip]` icon buttons rest in gray-500), and the root layout's
`ThemeProvider` keeps secondary buttons from turning blue on hover. The full
palette and rules are in DESIGN.md.
Shared CSS is in `src/app/globals.css`.

- Layout: `src/app/(app)/layout.tsx` with `<AppSidebar>`
  (`src/components/app-sidebar.tsx`). Every migrated page gets an entry in
  `NAV` there, under the right section, with a Material Symbols icon name.
- Forms: `<FormFields state defaults>` wrapping `TextField`, `TextareaField`,
  `SelectField`, `CheckboxField`, `Fieldset` and `FormButtons`
  (`src/components/form-fields.tsx`); people reuse `<PersonFields>` with
  `personFields` / `personUniqueError` (`src/lib/person.ts`). A form with rows
  added on the client (the student's guardians) submits via `onSubmit` +
  `startTransition`, so React doesn't reset it.
- Buttons: Flowbite `Button`; in Server Components use `<LinkButton>`
  (`src/components/link-button.tsx`), not `<Button as={Link}>`.
- Delete confirmation: `<DeleteButton action={deleteX.bind(null, id)} />`.
- Long selects: `<Combobox>` (`src/components/combobox.tsx`).
- Formatting (Brazilian Portuguese): `formatMoney`, `formatDate`
  (`src/lib/finance.ts`), `formatDocument`, `personKind`, `formatCpf`,
  `formatZipCode` (`src/lib/format.ts`), `formatGrade` (`src/lib/grades.ts`).
  Money and numbers are right-aligned and don't wrap (`<MoneyCell>`).

## Configuration

- `.env` (see `.env.example`): `DATABASE_URL`, `BETTER_AUTH_SECRET`,
  `BETTER_AUTH_URL`, `MEDIA_ROOT`, and `SEED_PASSWORD` (dev only).
- Dev database: the Docker container `gestao-pg`, started by `npm run dev`, `db:reset` and
  `db:migrate` when `DATABASE_URL` is local (`scripts/start-db.mts`; Postgres on `localhost:5433`,
  user / password / db `gestao`), then `npm run db:reset`.
- Production (Vercel + Neon): see README, "Deploy". In short: an empty
  `public` schema, `npm run db:migrate` and `npm run create-admin` with the
  direct Neon URL, the pooled URL in Vercel. Never `db:reset` or the seed there.
- Schema changes: edit `src/db/schema/app.ts`, run
  `npm run db:generate`, review the SQL in `drizzle/`, then `npm run db:migrate`.
  The app tables have no DB defaults for `created_at` / `updated_at`: the
  schema fills them with `.$defaultFn(...)` / `.$onUpdate(...)`, so keep that
  on new tables. Foreign keys are checked per statement (Django's were
  deferred to commit): delete children before parents in a transaction.
- Postgres `numeric` comes back as `string`; money math uses `decimal.js`,
  never `number`.

## Testing

Vitest (`npm test`). The rules in `src/lib/` have unit tests next to them
(`finance.test.ts`, `finance-db.test.ts`, `grades.test.ts`, `form.test.ts`,
`format.test.ts`, `list.test.ts`, `students.test.ts`); `finance.ts` is checked
against Django's results on random contracts. New rules come with tests in
the same style. Pages and actions have no automated tests yet.
